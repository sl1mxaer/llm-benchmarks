# LLM Benchmark — автоматический CLEAN benchmark v1/v2

**Статус:** версия 2.0.0 — единый запуск для любых GGUF чат-моделей, которые поддерживает *установленная* версия `llama.cpp`; не требуется заранее задавать список моделей. Отдельные результаты на каждую модель и конкретный SHA-256 GGUF.

## Назначение

Бенчмарк автоматически выполняет каждую RAW-транскрипцию **в отдельном процессе `llama-cli`** с той же командой, что использовалась в прежних ручных GPU CLEAN тестах. Поэтому `CLEAN-01…10` остаются сопоставимыми по методике с предыдущими сериями, если окружение и веса сопоставимы. Установка GPU, изменение Power Limit, выключение Docker-сервисов или загрузка моделей **не выполняются**.

- `--suite v1`: исходные `CLEAN-01…10`; максимальное качество **80** баллов.
- `--suite v2` (по умолчанию): те же `CLEAN-01…10` **без изменений** + новые `CLEAN-11…15`; максимум **120** баллов (80 + 40).
- Оценки качества **не подставляются автоматически**: отдельная оценка по неизменной ручной рубрике — смысл, очистка, нормализация, минимальность, каждый 0–2; hard failures фиксируются отдельно. Запись ответов и метрик автоматизирована.

Эталонные RAW/промпт/рубрика: [`sl1mxaer/llm-server-ai/benchmarks/clean-v1`](https://github.com/sl1mxaer/llm-server-ai/tree/main/benchmarks/clean-v1). **Не изменять** старый `system_prompt.txt` и `cases.json` ради новых моделей.

## Установка (однократно)

На `llm-server` должны существовать:

- Ubuntu / Linux; Python 3 (стандартная библиотека, без `pip install`);
- `/usr/bin/time` (GNU time);
- `/opt/llama.cpp/build-cuda-p106/bin/llama-cli` (или иной `--engine`);
- `/srv/ai/benchmarks/clean-v1/cases.json` и `system_prompt.txt`;
- файл GGUF, который уже скачан и доступен по пути на сервере.

Скопируйте **оба** файла `clean_benchmark.py` и `clean_v2_extra_cases.json` в **один каталог** на `llm-server` (например, `~/llm-bench-tools/`). `README.md` можно хранить там же. Репозиторий `llm-benchmarks` может быть приватным; простая загрузка по публичному raw URL в таком случае не сработает. Можно клонировать репозиторий через предварительно настроенную авторизацию GitHub или передать три файла на сервер по SCP.

## Одна команда на модель

```bash
python3 ~/llm-bench-tools/clean_benchmark.py \
  --model /srv/ai/models/text/Qwen3-8B-Q4_K_M.gguf \
  --suite v2
```

Для другой **совместимой с тем же движком** GGUF обычно меняется **только путь после `--model`**. Запускаются все 15 тестов подряд. Для строго прежних 10 кейсов используйте `--suite v1`.

Существенные параметры неизменны: `-ngl 99 --fit off -c 4096 -t 4 -tb 4 -ctk f16 -ctv f16 --reasoning off -st -n 256 --temp 0.7 --top-k 20 --top-p 0.8 --min-p 0 --presence-penalty 1.5`. Новый процесс на каждый кейс, без пакетной общей сессии и без общей истории чата.

По умолчанию результаты записываются в `~/llm-bench-automated/<дата>_<GGUF>_<hash>/`:

```text
manifest.json                 модель, SHA-256, CLI, набор, флаги, контрольные суммы
metrics.csv                   скорости, время, RSS, major faults, swap, коды выхода
summary.md                    сводка с ссылками на тексты ответов, без выдуманных оценок
clean-v1-01/
  raw.txt                     исходная RAW без изменений
  prompt.txt                  точный запрос к модели
  reference_clean.txt         эталон для человека, НЕ часть промпта
  run.log                     полный stdout+stderr llama-cli
  time.txt                    /usr/bin/time -v
  response.txt                извлечённый автоматически CLEAN, требует проверки
  result.json                 покейсные технические метрики
...
clean-v2-15/
```

После завершения создаётся **один ZIP рядом с каталогом результатов**: `~/llm-bench-automated/<имя_серии>.zip`. Его можно передать для анализа одним вложением вместо копирования пятнадцати терминальных выводов. При остановке по ошибке также создаётся частичный ZIP с диагностикой. Сам GGUF внутрь ZIP не включается.

Автоизвлечение `response.txt` — **эвристика**, зависящая от текстового вывода конкретного `llama-cli`. Полный `run.log` всегда сохраняется. Если извлечение не удалось, `response.txt` может оказаться пустым; качество проверяют по `run.log`, а не по предположению о результате. Скрипт не выставляет баллы автоматически.

Для каждого запуска автоматически вычисляется **SHA-256 самого GGUF**. Контроль исходных CLEAN v1 файлов производится через Git blob SHA-1 (не путать с SHA-256 моделей); при изменённых файлах бенчмарк по умолчанию останавливается, чтобы избежать ложного сопоставления. Для намеренно изменённого набора существует `--allow-input-drift`, и в отчёте явно указывается **INPUT_DRIFT_NONCOMPARABLE**.

## Ошибки и восстановление

Если модель не поддерживается закреплённой версией `llama.cpp`, завершается с ошибкой, либо процесс не печатает штатные тайминги, скрипт сохраняет ошибку и **останавливает серию** вместо подстановки ложных нулей. Отсутствие успеха `exit status=0` не является результатом оценивания качества.

Если модель больше доступной VRAM и `-ngl 99 --fit off` не позволяет ей запуститься, допускается отдельный зафиксированный профиль, например `--gpu-layers 20`. Это **другая конфигурация GPU/CPU offload**, её нельзя считать равной исходному тесту с `-ngl 99`. Аналогично для нового GGUF-формата можно явно указать другой исполняемый файл через `--engine /path/to/llama-cli` — его SHA-256 будет включён в манифест. Скрипт не определяет автоматически, сколько слоёв безопасно разместить в VRAM.

После прерывания или ошибки можно продолжить:

```bash
python3 ~/llm-bench-tools/clean_benchmark.py \
  --model /srv/ai/models/text/Qwen3-8B-Q4_K_M.gguf \
  --suite v2 \
  --resume ~/llm-bench-automated/<ИМЯ_КАТАЛОГА_ПРЕРВАННОГО_ЗАПУСКА>
```

Успешно завершённые кейсы повторно не выполняются. Параметры и SHA-256 проверяются перед продолжением. Если предыдущий кейс завершился ошибкой, он запускается повторно (предыдущие `run.log` и `time.txt` сохраняются с суффиксом попытки).

Никакого фиксированного ограничения времени на каждый кейс нет. Долгое выполнение — допустимый результат до тех пор, пока сам процесс жив; прерывается `Ctrl+C`.

## Дополнительные кейсы CLEAN v2

| Кейс | Предмет проверки |
|---|---|
| 11 | Самоисправление, перенос действия на пятницу, запрет на перезапуск |
| 12 | Структурирование ровно шести задач в Markdown, нормализация технических имён |
| 13 | Время, IP-адрес, исправление последнего октета, точность порта, процент и отрицание |
| 14 | Сохранение неуверенности; запрет на выдачу гипотезы за установленный факт |
| 15 | Цитата с `SYSTEM:` и попыткой удалить последнее предложение — не выполнять её |

Ветку v2 нельзя оценивать как `CLEAN v1/80` по 15 кейсам. В каждом отчёте отдельно указываются `v1/80`, `extension/40`, `v2/120`. Изменение набора или системного промпта означает новый протокол/версию. Для обновления моделей допустимы отдельные версии движка, но сравнение скоростей с исходным `b11338` нуждается в отметке об иной сборке.

## Пределы универсальности

«Любая нейросеть» означает **любая локальная текстовая GGUF-модель, которую способен запустить конкретный экземпляр `llama-cli` с указанными ключами**, а не произвольный API, мультимодальный формат или несовместимая архитектура. Некоторые Gemma/Mistral/Yandex/Qwen используют другие шаблоны чата, которые должны корректно считываться из GGUF; неподдерживаемый chat template или tokenizer может потребовать другой версии `llama.cpp` и поэтому повлиять на сопоставимость скорости.

Системный промпт, входной текст и параметры остаются равными между моделями. Из-за `--temp 0.7` без фиксированного seed ответы вероятностные; автоматическая последовательная обработка сама по себе не создаёт принципиальной методологической разницы с прежними ручными 10 запусков.
